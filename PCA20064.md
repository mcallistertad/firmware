# PCA20064 nRF9161 compatibility

This branch adds the pre-production Thingy:91 X PCA20064 as a native target for
Hello nRF Cloud firmware v2.0.2. The prototype uses an nRF9161 instead of the
production nRF9151, but retains the nPM1300, nPM6001, nRF7002, BME688, external
32 MiB SPI NOR, RGB LED, button and nRF5340 USB connectivity bridge.

## Build

Initialize a workspace from this fork and branch:

```bash
west init -m https://github.com/mcallistertad/firmware \
  --mr pca20064-v2.0.2 hello-nrfcloud-pca20064
cd hello-nrfcloud-pca20064
west update
west zephyr-export
```

Build the complete B0, MCUboot, TF-M and application image:

```bash
west build -p always --sysbuild \
  -b pca20064/nrf9161/ns \
  project/app
```

The nRF7002 is configured for scan-only Wi-Fi location assistance. Cloud
transport remains LTE/CoAP. UART0 uses the installed nRF5340 USB bridge at
115200 baud; UART1 is reserved for modem trace handling.

## Programming safety

The PCA20064 uses B0 with a provisioned Nordic prototype trust anchor. Do not
replace the NSIB signing key or program an unsigned application. Use the
sysbuild `merged.hex` only for complete recovery. For ordinary updates, use the
MCUboot-signed application or the generated DFU package so B0 and MCUboot remain
installed.

The external-flash layout reserves space for MCUboot secondary, full-modem
FOTA, settings and modem traces.

## Cloud provisioning

No modem credentials, SIM identifiers, device serial numbers or private keys
are stored in this repository. Provision the device into nRF Cloud separately;
the application expects its nRF Cloud credentials in security tag 4242.

For a manually created nRF Cloud device, the firmware must use the exact client
ID associated with its certificate instead of the Hello production default of
`oob-<IMEI>`. Keep that selection in an ignored local configuration file:

```conf
CONFIG_NRF_CLOUD_CLIENT_ID_SRC_COMPILE_TIME=y
CONFIG_NRF_CLOUD_CLIENT_ID="<client-id-from-credentials-json>"
CONFIG_NRF_CLOUD_CLIENT_ID_PREFIX=""
```

Pass it to sysbuild with
`-Dapp_EXTRA_CONF_FILE=$PWD/.local/pca20064-device.conf`.

Before booting the cloud application, put the modem offline and install the
nRF Cloud CoAP root CA, client certificate and private key as credential types
0, 1 and 2 under security tag 4242. The downloaded JSON and extracted PEM data
must remain outside version control with mode 0600. Do not use
`CONFIG_NRF_CLOUD_PROVISION_CERTIFICATES` for a deployable image because that
embeds the private key in readable application flash.

## Secure per-device deployment

A plain build is intentionally convenient for board recovery and development, but
inherits public evaluation signing keys from the Nordic reference configuration.
Do not install cloud credentials on that image.

For a credentialed device, keep all identity and key material in the ignored
.local/ directory and build with both local fragments:

~~~sh
west build -p always -b pca20064/nrf9161/ns app --sysbuild -- \
  -Dapp_EXTRA_CONF_FILE="$PWD/.local/pca20064-device.conf" \
  -DSB_EXTRA_CONF_FILE="$PWD/.local/pca20064-secure.conf"
~~~

The device fragment selects the exact nRF Cloud device ID. The sysbuild fragment
must point at unique P-256 keys for NSIB/B0 and MCUboot and should contain:

~~~ini
SB_CONFIG_SECURE_BOOT_SIGNING_KEY_FILE="/absolute/path/to/nsib-signing.pem"
SB_CONFIG_BOOT_SIGNATURE_KEY_FILE="/absolute/path/to/mcuboot-signing.pem"
SB_CONFIG_APPROTECT_LOCK=y
SB_CONFIG_SECURE_APPROTECT_LOCK=y
~~~

Back up both signing keys in encrypted offline storage. Losing either key prevents
normal signed updates; recovery then requires a mass erase and reprovisioning.
Never commit the fragments, signing keys, downloaded credential JSON, client
certificate, or private key.

After recovering a prototype that previously used evaluation keys, program the
complete merged.hex once to establish the new B0/MCUboot trust chain. Use the
generated signed DFU package for subsequent application updates.

AP-Protect closes debug access but deliberately leaves chip recovery available for
development. It does not protect modem credentials against a physical attacker
who can recover the application core and install firmware that uses those opaque
credentials. A production product also needs erase-all protection, but enable it
only after its signed DFU and product recovery path have been tested; incorrect
use can permanently remove the development recovery path.

The Hello firmware uses coap.nrfcloud.com, security tag 4242, and the nRF Cloud
CoAP message resource. The MQTT endpoint and generated SenML topic shown by the
portal are cloud routing metadata, not additional firmware credentials. Provision
the combined production AWS and CoAP root CA as credential type 0, the device
certificate as type 1, and the private key as type 2, all under security tag 4242.
Keep the modem offline while modifying credentials.

## Reporting liveness

After each cloud connection, the PCA20064 sends one immediate device,
sensor/battery and location update, then enters its normal low-power cadence.
The normal reporting interval and requested PSM periodic TAU are 12 hours. The
nRF Cloud device shadow may request a longer interval, but values shorter than
12 hours are clamped locally. A button press still requests an immediate report.
When that immediate poll starts a location search, blue remains visible for one
second as acknowledgement before the location-search indication changes to
green.

The PCA20064 application enables the RGB status LED. It breathes yellow while
LTE is connecting, blue while polling, green during a location search, purple
during FOTA, and red for faults. The normal 12-hour low-power state is dark;
the LED module suspends PWM0 while the LED is off. LTE/IP modem trace generation
is also disabled in the production profile to avoid continuous background
writes to external flash.

A location request may suppress new triggers for at most 180 seconds. If the
location library fails to deliver its terminal event, cloud and FOTA polling
resume automatically instead of leaving the device permanently blocked. The
task watchdog also uses the nRF9161 hardware watchdog as a fallback, so a kernel
or scheduler stall resets the application even when the software watchdog timer
cannot run.

The application also treats terminal access, connection-reset, shutdown,
timeout, I/O and protocol failures from confirmed CoAP operations as evidence
that the retained cloud session is unusable. Payload, shadow, FOTA and
cloud-assisted location paths request one deduplicated disconnect/reconnect;
the disconnect cancels the current report cycle and a ready replacement session
starts one fresh cycle. This prevents shadow, FOTA and location requests from
serially waiting on the same stale CoAP session while the LED remains green.
